# 混合同步比例基准设计

## 目标

比较 EXT2、EXT4 writeback 和 rNVPCe-SU 在混合读写负载下，随写后 `fsync()`
注入比例增加时的吞吐量和延迟变化。实验不使用 fio，而使用可复现的专用用户态
程序，确保同一读写比例下不同同步比例采用相同的读写类型和页面地址序列。

## 固定矩阵

- 请求大小：4 KiB，页对齐随机访问。
- 并发：8 个线程，每线程独占一个普通文件和文件描述符。
- 读写比例：0:10、3:7、5:5、7:3。
- 写后 `fsync()` 比例：0%、20%、40%、60%、80%、100%。
- 文件系统：EXT2、EXT4 journal、rNVPCe nojournal + soft update + rTIO。
- 设备：SATA 使用 1 个 virtqueue；NVMe 使用 8 个 virtqueue。
- 重复：每个坐标 3 轮。
- 时间：预热 10 秒，正式测量 30 秒。
- 缓存预算：256 MiB；工作集约为其十倍，即总计 2560 MiB，每线程 320 MiB。

每个文件在正式测试前完整预写并执行同步。正式测试只覆盖已分配范围，因此写请求
不包含首次数据块、位图、extent 或 inode 扩展分配成本。

## 可复现操作序列

基准程序使用固定主种子。每次操作的读写类型、页号和是否执行 `fsync()` 分别由
`(seed, thread_id, operation_index, decision_kind)` 派生，不能共享一个会因分支而改变
后续结果的 PRNG 状态。这样，同一读写比例下的所有同步比例具有完全相同的访问
序列；同步阈值采用同一个均匀值，使 20% 的同步写集合是 40% 集合的子集。

同步写定义为一次成功的 `pwrite()` 后立即在同一文件描述符上调用 `fsync()`。
`fsync()` 会同步该文件此前所有未持久化修改，因此横坐标名称为 `fsync injection
ratio`，不能表述为“只有所选写的数据被持久化”。

## 缓存口径

- EXT4：DRAM PageCache 容量设为 256 MiB。
- rNVPCe：DRAM PageCache 128 MiB，NV data capacity 128 MiB，总计 256 MiB；NVM
  metadata reserve 单独记录，不计入数据缓存预算。
- EXT2：当前实现没有与 EXT4 `pagecache_capacity_mb` 等价的文件系统级容量控制。
  runner 和报告必须明确记录这一事实以及 VM 内存配置，不能声称 EXT2 实际缓存被
  严格限制为 256 MiB。若后续增加 EXT2 容量控制，再将其标记为严格可比数据。

每个结果必须保存配置预算、工作集大小、预写字节数、VM 内存、挂载参数和可获得的
缓存/内存计数。配置值与运行时观测值分列，不能用配置值冒充实际使用量。

## 统计与产物

程序输出 JSON，至少包含操作总数、读写次数、成功 `fsync()` 次数、实际比例、读写
吞吐量、总吞吐量、平均延迟以及 p50/p95/p99/p99.9 延迟。预热数据不计入正式统计。
错误、短 I/O、预写不完整、比例超出可解释误差或清理失败均使测试点失败。

外层 runner 复用现有真实分区容量、挂载、holder、打开用户和 e2fsck 检查。原始
逐轮 JSON、CSV 聚合、绘图输入、图片和中文复现说明归档到同一个测试结果目录。

## 非目标

- 不测首次分配写性能。
- 不使用 `O_SYNC`、`O_DSYNC` 或尚未实现语义的 `RWF_SYNC/RWF_DSYNC`。
- 不把测试结束后的全局 `sync` 时间计入正式测量窗口。
- 不用本实验推导 SATA 多硬件队列能力。
