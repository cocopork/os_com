# 前期 EXT4 / rNVPC / rNVPCe 性能扫描规范

## 定位

本测试是开发冒烟验证之后、论文正式评测之前的前期性能扫描。其目的不是生成
论文数据，也不是替代每次功能开发后的快速验证，而是在一个机制基本可用后，以
较完整的工作负载矩阵观察吞吐扩展性、块大小敏感性和尾延迟，发现仍需延迟分解
或针对性诊断的性能瓶颈。

本测试固定使用2 GiB工作集和128 MiB模拟NVDIMM池。该配置缩短迭代时间，不能
与论文中16 GiB NVDIMM、128 GiB工作集的结果直接比较，也不能写入论文正式结果
图表。测试结果只能描述当前代码、当前设备和本规范所列配置下的性能。

## 性能验证层级

| 层级 | 使用时机 | 负载范围 | 结论范围 |
|---|---|---|---|
| 开发快速验证 | 引入或修改一个机制后 | 4 KiB随机写、128 KiB顺序写；通常1/16线程 | 发现明显功能错误或数量级性能回退 |
| 前期性能扫描 | 快速验证基本正常后 | 本文规定的thread sweep和bs sweep | 定位扩展性、块大小敏感性和后续诊断方向 |
| 论文正式评测 | 前期扫描未发现阻塞问题后 | 论文规定的设备、容量、工作集、重复次数和比较对象 | 形成可用于论文的重复测量和统计结论 |

三个层级的结果必须分别保存和命名。不得用开发快速验证或前期性能扫描的结果
替代论文正式评测，也不得将不同层级的数据拼接为同一条曲线。

## 比较对象

| 名称 | 数据路径 | 持久性机制 | 挂载配置 |
|---|---|---|---|
| EXT4 writeback | 原生DRAM PageCache与EXT4后台写回 | JBD2 journal | `delalloc,rnvpc=off,rnvpc_extend=off,rtio=off` |
| rNVPC WAL + rTIO | WAL保护的rNVPC与rTIO写回 | rNVPC WAL；不以JBD2作为持久性机制 | `delalloc,rnvpc=on,rnvpc_extend=off,rtio=on` |
| rNVPCe + rTIO | NVPage持久数据面、soft-update元数据协议与rTIO | soft update；不以JBD2作为持久性机制 | `delalloc,rnvpc=off,rnvpc_extend=on,rtio=on` |

原生EXT4与两种NVM模式采用不同的预期持久性机制，因此该比较不是单变量消融
实验。rNVPC和rNVPCe测试应确认运行时没有启动JBD2；若当前rNVPC实现只能在
带journal的磁盘格式上运行，则结果必须标记为实现偏差，不能直接作为表中
“rNVPC WAL + rTIO”的结果。每个测试点应记录磁盘`HAS_JOURNAL`特性和运行时
journal状态，避免根据请求参数推断实际状态。

## 固定环境

- 设备：仅使用授权的NVMe测试分区，当前为`/dev/nvme1n1p1`；本阶段不测SATA。
- 每个测试点重新格式化文件系统，不复用上一点的文件系统状态。
- QEMU/KVM：64 vCPU、8 GiB guest内存。
- virtio-blk：单队列、queue size 1024、`cache=none,aio=threads`。
- CPU放置：fio使用CPU0--31，原生writeback使用CPU60，virtio提交使用CPU62，
  journal使用CPU63；rTIO线程使用普通内核线程CPU集合32--59。
- 模拟NVDIMM：`rnvpc_size=128M`、`rnvpc_meta_reserve=64M`、
  `rnvpc_data_limit=64M`、`rnvpc_sim_mode=fast`。
- 吞吐测试使用release、error级日志，关闭延迟插桩、分配器统计和逐操作日志。
- fio：`ioengine=psync,direct=0,fsync=0,iodepth=1,thread=1`，每个job独立文件，
  `group_reporting=1,fallocate=none`。
- 每点总工作集约2 GiB。不能整除线程数时，每个job使用
  `floor(2048 / jobs)` MiB，并以实际完成字节数计算含sync带宽。
- 固定随机种子，并在manifest中记录代码提交、工作区状态、ISO哈希、设备身份、
  格式化参数、挂载参数和fio完整命令。

## 测试矩阵

### Thread sweep

对随机写和顺序写分别执行：

- 块大小固定为4 KiB；
- jobs为`1,4,8,12,16,20,24,28,32`；
- `randwrite`为已有文件上的随机覆盖写；
- `write`为fresh文件上的顺序首次写入。

随机覆盖写在测量前使用原生direct I/O顺序初始化每个job的完整文件范围，执行
`sync`并重新挂载，再启动被测模式。初始化耗时不计入测量，但其成功状态和完成
字节数必须保留。

### Block-size sweep

对随机写和顺序写分别执行：

- jobs固定为1；
- 块大小为`4,8,16,32,64,128,256,512,1024 KiB`；
- 随机写沿用完整范围预初始化规则；
- 顺序写使用fresh文件。

4 KiB、1线程会同时出现在thread sweep和bs sweep中。两个点均保留，不去重，
用作同批次重复观测；若差异明显，先进行重复测量，而不是从其中选择更有利的值。

三种模式共`3 x 2种负载 x 2种扫描 x 9个坐标 = 108`个测试点。不同模式、
负载和坐标串行执行，禁止共享测试分区或辅助镜像并发运行。

## 指标与有效性条件

每个测试点至少记录：

- fio工作阶段吞吐量（MiB/s）和IOPS；
- 从fio启动到最终`sync`返回的含sync吞吐量；
- fio平均完成延迟和P99完成延迟；
- fio实际完成字节数、运行时间和错误码；
- 最终`sync`耗时、卸载状态和QEMU退出状态；
- 后置`e2fsck -fn`结果；
- 随机写初始化阶段的完成字节数和状态。

只有同时满足以下条件的点才能进入比较表：fio错误码为0、完成预期字节数、最终
`sync`成功、正常卸载、guest完成标记存在、QEMU按约定退出、后置`e2fsck -fn`
通过。e2fsck只验证SSD文件系统结构，不证明rNVPC/rNVPCe掉电一致性或文件内容
正确；崩溃一致性必须由独立故障注入测试验证。

本阶段可以先执行每点一轮以发现瓶颈。任何将要作为优化前后收益依据、或用于判断
小于10%的性能变化的坐标，都必须在相同镜像和环境下至少重复3轮，并报告中位数
及最小/最大值。诊断插桩运行必须单独标记，其吞吐不能与未插桩运行直接比较。

## 结果解释和升级条件

前期扫描重点回答：

1. 随线程数增加，吞吐是否扩展，在哪个线程数达到峰值并开始下降；
2. 随块大小增加，顺序写是否保持连续BIO，随机写是否受逐页元数据操作限制；
3. fio吞吐与含sync吞吐的差距是否表明后台迁移或最终状态发布积压；
4. rNVPC WAL与rNVPCe的差异是否集中在前台持久化、rTIO提交或completion回收；
5. 4 KiB/1线程重复点的波动是否足以影响曲线解释。

若某一模式出现未完成、`ENOSPC`、`EIO`、卸载失败或结构检查失败，应先作为正确性
问题处理。若功能正确但出现明显平台期、随线程增加持续回退、特定块大小突降，或
fio与含sync吞吐差距持续扩大，再对代表坐标执行前台write、rTIO flush和completion
三阶段延迟分解。只有前期扫描没有未解释的主要回退，且关键点重复测量稳定后，才
进入论文正式评测。

## 与论文评测的边界

论文第6节正式微基准固定4 KiB，扫描`1,4,8,12,16,20,24,28,32`个fio jobs，
每个job使用独立文件，所有jobs合计遍历128 GiB地址范围，并同时测试SATA和NVMe。
论文环境还声明16 GiB NVDIMM。本文的bs sweep是为性能诊断增加的敏感性实验；
2 GiB工作集、128 MiB池和仅NVMe环境均属于前期测试缩放配置。

正式评测前必须另行冻结论文级配置、重复次数、运行顺序和统计方法。前期扫描报告
应明确写出“非论文正式数据”，不能将其峰值与历史论文图中的峰值直接计算提升比例。
