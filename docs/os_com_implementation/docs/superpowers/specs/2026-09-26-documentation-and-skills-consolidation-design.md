# os_com/AchillesFS 文档与开发经验整理设计

日期：2026-09-26

## 1. 目标

整理 `os_com_implementation` 的实验进展、设计文档和开发经验，形成少量权威入口；保留有研究价值的历史证据，删除未采用且不可形成结论的临时产物；将开发经验沉淀为两个项目内 Codex skill。

本次工作只整理文档、实验资产和 skill，不改变 `os_com` 文件系统行为，也不重新解释原始实验数值。

## 2. 权威文档结构

根目录建立四个主入口：

- `README.md`：项目定位、目录关系、阅读顺序和最短复现入口。
- `STATUS.md`：唯一的任务进度事实源，记录当前分支、已完成、进行中、阻塞项、验证状态和下一步。
- `EXPERIMENTS.md`：已采用实验的配置、结果、证据路径、结论和限制。
- `LESSONS.md`：面向开发者的已验证问题与经验摘要。

其余文档按职责收敛：

- `os_com_refactor_plan/README.md` 只维护任务总表，各任务 README 压缩为目标、状态、结果、证据和遗留问题。
- `rNVPC-rTIO/README.md` 作为 AchillesFS 设计入口；权威设计合并到 `design.md`，实现边界和任务状态合并到 `implementation.md`。
- `test/README.md` 说明统一测试环境和资源约束；各测试目录 README 只保留用途、参数、运行命令、产物格式和已知限制。
- `NEXT-SESSION.md` 不再作为独立进度源，其中仍有效的内容并入 `STATUS.md`、测试 README 或项目专用 skill。

当前事实只能写入主文档。归档材料只能作为证据被引用，不得继续声明当前进度。

## 3. 历史归档

历史材料按内容进入：

```text
archive/
├── design/
├── experiments/
└── debugging/
```

只归档具有下列价值之一的内容：

- 解释当前设计为何采用或放弃某条路线；
- 支撑已采用的研究结论；
- 记录关键故障根因和可迁移的方法学；
- 包含无法从当前代码或最终数据重新推导的证据。

归档文档必须在开头注明原始日期、归档原因、当前替代文档和是否仍可用于引用。

## 4. 实验资产保留与删除

正式实验统一整理为：

```text
evidence/<experiment-name>/
├── README.md
├── summary.csv
├── plot.py
└── figure.pdf/png
```

保留：

- 论文或当前设计结论直接采用的最终 `summary.csv`；
- 生成正式图片所需的绘图脚本和最终 PNG/PDF；
- 实验配置、代码版本、设备环境、口径和限制；
- 无法替代的关键故障证据，但整份日志应提炼为最小片段；
- 当前有效的一键运行、guest、解析和测试脚本。

删除：

- 未完成、超时、零轮、缺少完成标记的实验；
- 已被完整复测替代的早期重复矩阵；
- 未被论文、图片、设计或问题结论引用的数据；
- 原始 QEMU、串口、构建和 console 日志；
- 临时延迟分解 CSV/JSON、诊断快照、中间图片；
- 空结果目录、`__pycache__` 和可重新生成产物；
- 已否决且不具备方法学价值的实验数据。

执行删除前生成 `CLEANUP-MANIFEST.md`，逐项记录保留、归档或删除、理由、引用关系和预计释放空间。实际删除严格以该清单为边界。

## 5. 实验口径

- 正式吞吐结论、对比表和论文图片统一采用 `busy_bw_mib_s`。
- `drain bandwidth` 只用于诊断卸载、尾部排空和后台写回完成情况，不进入正式性能结论。
- 工作集、缓存容量、线程数、设备、虚拟机和插桩状态必须随结果记录。
- 测绝对性能时关闭延迟插桩；分解实验只能用于阶段占比和根因分析。
- 每个测试点必须有 guest 完成标记；静默退出、超时或不完整输出不得进入结果表。

## 6. 双层项目 Skill

两个 skill 均位于 `os_com_implementation/.codex/skills/`。

### 6.1 `filesystem-development`

保存与具体仓库无关的文件系统开发方法：

- 仅在引入新功能/机制或改变既有机制语义时，定义或更新故障模型、持久化边界、权威副本、状态机和恢复不变量；普通实现和不改变语义的重构继承既有定义。
- 正确性验证分为数据结构、状态机、纵向路径和崩溃恢复。
- 并发诊断覆盖锁序、completion 上下文、前后台竞争、重脏和 ABA。
- 性能诊断覆盖内存路径、分配、BIO 构造、提交、设备完成和后处理。
- 实验结果采用 busy bandwidth，并记录设备上限、缓存/工作集关系和插桩状态。
- 明确禁止中断上下文执行重型状态转换、每页同步等待、全树 flatten/rebuild，以及用单轮异常形成结论。
- 输出采用“假设、证据、修改、正确性门禁、性能门禁、残余风险”结构。

该 skill 不包含本机绝对路径、AchillesFS 状态或易过期实验数字。

### 6.2 `asterinas-ext4-achillesfs`

保存项目专用知识：

- `os_com`、`os_com_implementation`、测试和结果目录之间的关系；
- 容器、QEMU/KVM、virtio-blk、镜像和真实设备的隔离约束；
- EXT4/JBD2、PageCache dirty mark、delalloc、extent、metadata cache 和后台 writeback 的实现边界；
- AchillesFS 的 NVPage/NVBH、soft update、rNVPCe、rTIO 和恢复模型；
- completion 回调、QEMU 资源冲突、单次编译复用、插桩开关、guest 完成标记和容量压力测试等已验证问题；
- 当前有效的构建、测试和结果核验命令。

该 skill 首先引用 `filesystem-development`，再读取 `STATUS.md` 和 `EXPERIMENTS.md`，不复制易过期进度。

## 7. 执行阶段

1. **事实审计**：以 `os_com` 当前代码、提交历史和有效实验为准，将内容标为当前有效、历史有效、已取代或无法证实。
2. **主文档重写**：建立四个主入口，压缩任务、设计和测试文档，消除重复状态叙述。
3. **归档与清理**：移动关键历史材料，生成清理清单，按清单删除临时和无效产物。
4. **Skill 固化**：创建两个 skill，验证触发范围、引用路径、命令和职责隔离。

## 8. 验收标准

- 从根 README 出发三次跳转内可找到当前进度、权威设计、实验结论和复现命令。
- 当前进度只在 `STATUS.md` 维护，主文档不存在互相矛盾的状态。
- 每个正式结论都可追溯到保留的 `summary.csv` 或明确代码证据。
- 正式性能数据全部使用 `busy_bw_mib_s`。
- 两个 skill 通过结构检查；通用 skill 不依赖项目路径，专用 skill 不嵌入易过期进度。
- 清理前后记录文件数量、空间占用和删除清单。
- 不修改最终采用 CSV 的原始数值，不删除仍被主文档或正式图片引用的证据。

## 9. 非目标

- 不修改 `os_com` 内核代码或文件系统语义。
- 不重新运行性能矩阵来填补缺失数据。
- 不把所有历史日志都归档。
- 不把论文叙事文档与工程状态文档合并为同一事实源。
