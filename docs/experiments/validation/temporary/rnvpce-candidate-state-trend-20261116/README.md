# rNVPCe 候选页状态趋势实验（2026-11-16）

## 目的

验证 4/8/12/16/20/24/28/32 个前台随机写线程下，rTIO worker 每轮能够 claim 的 NVPage 是否随
线程数增加而减少，并区分以下原因：

- owner worker 的 queued dirty 页不足；
- 页面已在 I/O in-flight；
- 页面等待 completion 处理；
- 页面已经完成迁移、等待前台并行回收；
- ready-inode 队列为空、节点失效或 entry 状态冲突。

## 条件

- 分支工作树：`optimize/rnvpce-owner-scheduling`
- 基础提交：`cce2180a2bdf324f9032633800a5f0eb6cd6e186`
- 设备：`/dev/nvme1n1p2`
- 负载：2 GiB、4 KiB 随机覆盖写、psync、direct I/O
- 文件：每 job 一个预分配、低碎片文件
- rNVPCe 数据容量：64 MiB，即 16,384 个 4 KiB NVPage
- rTIO：4 个 owner worker、4 个 virtqueue
- 线程数：4、8、12、16、20、24、28、32
- 诊断 ISO SHA-256：`5fc6fda5756a264479b4d5a0976761dad8ad58e340dbc785c25d9f32b3c460e0`
- 原始结果：`/home/zn/asterinas-build-env/rnvpce-candidate-state-20261116/results`

八个测试点均完成 sync、卸载及 e2fsck 校验。

## 新增诊断

每次 worker 完成候选 claim 后记录：

- 本轮 claim 页数；
- claim 前该 worker 的 queued、in-flight、completion-pending 页数；
- mount 全局 reclaim-pending 页数；
- 本轮是否处于容量或显式进度压力；
- ready-inode 出队为空、失效节点和 `Dirty -> Migrating` 状态冲突次数。

这些数值是按候选轮次采样的事件加权均值，不是同一时刻的全池原子快照。尤其
reclaim-pending 是 mount 全局值，其余三个状态是当前 worker 的本地值，因此不能把
各列相加作为精确池占用量。

时间没有增加，见下表。它更像压力流水线中的积压状态，而不是昂贵的 completion

24--32 线程的失效节点均为零，entry 状态冲突相对于数万个候选轮次可以忽略。因此
此前“主要是 Extending entry 无法 claim”的解释不成立。`ready_inode_empty` 接近候选
轮次数，是 worker 把当时少量可用 entry 消耗完后发现本地队列为空，不是 stale 节点
清理失败。

completion 总 CPU 时间在 32 线程仍只有 0.53 秒；真正爆炸的是 capacity wait、前台
reclaim-help 和由压力引起的候选轮次。候选选择单次并没有变慢，17.83 秒总时间来自
约 4 万次小轮次调用。

## 结论

实验确认“线程越多，每轮找到的可迁移页越少”不是从 4 到 32 的平滑单调趋势。20
线程出现前兆，24 线程首次发生断崖，并持续到 28/32 线程。直接原因是：

1. 24 个及以上前台线程更快耗尽 64 MiB 池，并同时进入容量等待/回收帮助路径；
2. 迁移完成的页面大量积压在 reclaim-pending，不能再次成为迁移候选；
3. 容量压力又持续唤醒全部 worker；worker 本地只看到约 18 个 queued 页，提交约 13
   页后立即再次空转；
4. 因而形成“容量压力 -> 小批次候选/空队列 -> 前台细粒度回收 -> 再次压力”的反馈环。

所以“64 MiB 池满后每个 worker 理应有约 16 MiB 可迁移页”的推断不成立：池容量包含
dirty、in-flight、completion-pending 和 reclaim-pending 多种状态；24/32 线程采样时
绝大部分容量已经在最后一种状态，而不是 worker 可 claim 的 dirty 状态。

后续优化重点应从候选索引转到回收发布：批量化/分散化 `help_nv_reclaim()`，并避免在
容量短缺主要由 reclaim-pending 构成时反复唤醒候选 worker。只有存在足够 queued dirty
页时才应启动新的迁移轮次。

## 后续验证：仅后台回收

关闭前台帮助回收、让单个后台helper始终以1,024页预算运行的诊断spike没有改善该问题。
16/20/24/28/32线程带宽分别降至`186/54/189/46/39 MiB/s`。原因是当前大预算只合并
helper调用，内部仍逐entry执行持久化、索引删除、allocator释放和容量唤醒；单后台线程
成为新的串行瓶颈，并使迁移退化为1--5页小批次。完整数据见
[`rnvpce-background-only-reclaim-spike-20261116`](../rnvpce-background-only-reclaim-spike-20261116/README.md)。
