# rNVPCe 前台最小 32 页回收批次验证（2026-11-16）

## 假设

当前 4 KiB 随机写在容量不足时调用 `help_nv_reclaim(1)`。本实验参考 Linux direct
reclaim 的最小回收簇，将前台 helper 的预算改为
`max(requested_pages, 32)`，验证减少单页 helper 调用能否消除 24--32 线程性能断崖。

实验只改变前台 helper 的取队列预算。后台 helper、迁移触发、候选选择、持久化协议、
每个 redirect entry 的回收实现和容量通知均不变。实验结束后该代码改动已撤销。

## 环境

- 设备：`/dev/nvme1n1p2`；每个测试点重新格式化并在结束后执行 e2fsck。
- 负载：2 GiB、4 KiB 随机覆盖写、psync、direct I/O。
- 文件：每 job 一个预分配、低碎片文件。
- VM：64 vCPU、8 GiB DRAM。
- rNVPCe：128 MiB NVM 池、64 MiB data limit、4 个 rTIO worker、4 个 virtqueue。
- profiling：关闭。
- 镜像 SHA-256：`4a6138669ae5efb36550a4202c3d100afcd578fc5184f0fea33811ce2c9c7b87`。
- 原始数据：`/home/zn/asterinas-build-env/rnvpce-foreground-batch32-20261116`。

所有测试点均完成 fio、sync、卸载和 e2fsck。16、24、32 线程重复三轮；其余点一轮，
用于快速观察趋势。

## 结果

| 前台线程 | 原策略 MiB/s | 32 页策略 MiB/s | 变化 |
| ---: | ---: | ---: | ---: |
| 4 | 535.99 | 555.77 | +3.7% |
| 16 | 634.45 | 386.82（三轮均值：423.05 / 368.74 / 368.68） | -39.0% |
| 20 | 494.07 | 334.92 | -32.2% |
| 24 | 258.82 | 352.68（三轮均值：353.55 / 327.55 / 376.94） | +36.3% |
| 28 | 204.87 | 179.41 | -12.4% |
| 32 | 268.20 | 162.60（三轮均值：176.69 / 162.48 / 148.62） | -39.4% |

16、24、32 线程三轮平均写延迟分别为 153.39、254.09 和 751.20 us。32 线程不但没有
恢复到 4--16 线程水平，带宽还稳定低于原策略。

## 结论

实验否定“只把每个前台 helper 的预算从 1 页提高到 32 页即可解决断崖”的假设。
增加预算能在个别并发点减少细粒度调用，但当前多个前台 helper 仍共同竞争一个全局
reclaim 队列，并且认领后仍逐 entry 执行持久化、索引删除、slot 归还和容量唤醒。
较大的单 helper 预算会让部分线程一次占有更多 ready work，降低其他等待线程取得容量的
公平性；不同并发点因此出现明显且不可接受的性能摆动。

下一步不应继续调大单个 helper 的预算。需要先把 reclaim 工作按 allocator/owner domain
分区，或为 helper 提供互不竞争的本地队列；随后再在每个分区内合并 redirect 发布、
slot 归还和容量通知。批量粒度应由可回收工作量和压力决定，而不是直接等于本次前台
申请页数或固定常量。
